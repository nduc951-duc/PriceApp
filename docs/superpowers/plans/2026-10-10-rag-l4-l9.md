# PriceApp RAG L4–L9 Execution Plan

> **For agentic workers:** Execute independent tasks in isolated worktrees. Keep each task within its listed files and report the commit, checks, and blockers.

**Goal:** Complete the remaining RAG levels with auditable retrieval, grounded citations, safe follow-up/cart handoff, reproducible evaluation, and a truthful demo package.

**Architecture:** Preserve the existing Fastify API, Supabase RLS/RPC price path, and Next.js UI. Separate query understanding, evidence verification, conversation state, evaluation, and demo documentation; keep SQL prices out of embeddings and LLM-authored SQL.

**Source requirements:** `docs/PRICEAPP_RAG_ROADMAP.md` and `docs/L4_L9_EXECUTION.md`.

## Global Constraints

- `public.prices.amount` remains authoritative and is returned only from current SQL rows.
- Never approve OCR/catalog data automatically or claim benchmark results without adjudicated labels.
- Preserve owner-only admin, user-scoped conversation RLS, `private, no-store` responses, and audited price writes with `expected_version`.
- No user/session text, auth tokens, provider keys, or raw provider errors in shared logs.

## Review Focus

- Ambiguous dimensions, package units, and price tiers must lead to clarification instead of a nearby catalog hit.
- An LLM response cannot add variant, package, or price IDs beyond the verified backend context.
- Citations must identify source page, chunk revision, and source span; duplicate evidence on one page must not be collapsed.
- Follow-up context must be isolated by user/session and re-fetch current prices before cart handoff.
- Evaluation outputs must distinguish candidate labels from owner-adjudicated truth and report failures as well as gains.

---

## Execution Order

1. **L4 audit and local completion:** review existing generation/checkpoint code and L3 migration; verify migration ordering and local gates. Cloud apply, owner index run, failure/resume and revocation acceptance require the authorized Supabase environment and approved corpus; do not fabricate evidence.
2. **Parallel independent work:**
   - L5 query understanding/parser and hard-filter primitives in new `backend/src/rag/query-understanding.ts` plus its focused tests.
   - L6 citation integrity types/helpers in new `backend/src/rag/citations.ts` plus focused tests; do not change query service/contract in this task.
   - L8 evaluation metric and dataset-splitting utilities in new `backend/src/rag/evaluation.ts` plus focused tests; mark all unlabeled examples as candidates.
3. **Serial integration:** integrate L5 and L6 into query service, versioned contracts, and admin debug UI; then implement L7 conversation/session and explicit cart handoff.
4. **L8 integration:** use the evaluation primitives with an owner-adjudicated corpus only; publish no scores until labels are approved.
5. **L9:** update setup/demo documentation and diagrams after interfaces settle; report cloud and owner-session blockers plainly.

## Completion Contract

- For code tasks, run the directly relevant tests, typecheck, lint, OpenAPI check, and build as applicable; read the full output.
- Keep each workstream's files and commit isolated; integrate only after scope review.
- Do not mark roadmap tasks complete when cloud/database/corpus acceptance remains unproven.
